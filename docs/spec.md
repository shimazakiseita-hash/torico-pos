# 仕様書 — やきとり TORI♡CO 注文・会計アプリ（torico-pos）

寮祭の `taiyaki-pos` をベースに改修する。**「寮祭からの変更」と書いた箇所が差分**。それ以外は既存の実装・挙動を踏襲する。

## 1. 運用の前提

| 項目 | 内容 | 寮祭からの変更 |
|---|---|---|
| イベント | 津田沼祭 2026年11月21日（土）・22日（日）の2日間 | 1日 → **2日** |
| 店名 | やきとり TORI♡CO（寮友会執行役員会） | 変更 |
| 提供方式 | 先に会計 → 呼び出し番号を発行 → 焼き上がったら番号で呼んで受け渡し | 同じ |
| 支払い | **現金のみ**。全品100円なので合計は必ず100円単位 | 金券 → **現金（お釣りあり）** |
| 端末 | PC 4台：受付 / 焼き場 / 渡し場（店員用）/ 渡し場（お客さん用）。＋責任者のスマホ（任意） | 2台 → **4台** |
| ネットワーク | 店内：サーバーPC（Ubuntu 26.04）が自分でWi-Fiアクセスポイントになる。**注文・会計はインターネットなしで動く** | **変更**（`docs/network.md`） |
| 整理券 | 番号ごとのQR付き。お客さんはスマホで呼び出し状況・待ち時間・ミニゲームを見られる。**この機能だけサーバーPCのインターネット接続が必要** | 寮祭と同じ仕組み |
| 環境 | 開発：WSL2 Ubuntu 24.04 ／ 本番：ネイティブ Ubuntu 26.04 | 変更 |

## 2. メニューと料金

串5種 × 味付け2種 = **10品目（SKU）**、すべて **1本100円**。セット割引なし。

| item id | 表示名 | | seasoning id | 表示名 | 色 |
|---|---|---|---|---|---|
| `momo` | もも | | `tare` | たれ | 茶系 |
| `kawa` | かわ | | `shio` | 塩 | 水色系 |
| `negima` | ねぎま | | | | |
| `tsukune` | つくね | | | | |
| `bonjiri` | ぼんじり | | | | |

- SKUは `(item, seasoning)` の組。表示順は上の表の順（もも→ぼんじり、たれ→塩）
- 合計金額 = 総本数 × 単価（100円）。単価は `src/lib/menu.ts` の定数に置き、ハードコードを散らさない
- 1注文の総本数は 1〜50 本
- 寮祭の「3個で500円」のセット計算ロジックとそのテストは**削除**する

## 3. 営業日（寮祭からの変更）

- `business_day` = 注文作成時の **Asia/Tokyo の日付**（`YYYY-MM-DD`）。サーバーPCの時計を使う
- **呼び出し番号は営業日ごとに1から振り直す**。`(business_day, number)` で一意
- 各画面は「今日の営業日」の注文だけを表示する。管理画面だけ日付を切り替えて過去日を見られる
- 仕込み数・釣り銭準備金は営業日ごとに設定する
- 2日目の朝に何か操作をする必要はない（日付が変われば自動で新しい営業日になる）

## 4. 注文の状態遷移（既存と同じ）

```
waiting（調理待ち） → ready（呼び出し中） → served（受け渡し済み）
waiting → cancelled（取り消し・返金）
ready → waiting（「完成」の押し間違いを戻す）
served → ready（「渡した」の押し間違いを戻す）
```
上記以外は 409。「完成」（→ ready）と、その取り消し（ready → waiting）は**焼き場**、「渡した」（→ served）と、その取り消し（served → ready）は**渡し場（店員用）**が押す。

## 5. データモデル（SQLite、`data/torico.db`）

寮祭のDBは引き継がない。新しいファイルで作り直す。

```sql
CREATE TABLE orders (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  business_day TEXT NOT NULL,                 -- 'YYYY-MM-DD' (JST)
  number       INTEGER NOT NULL,              -- 営業日ごとに1からの連番
  status       TEXT NOT NULL CHECK (status IN ('waiting','ready','served','cancelled')),
  total_qty    INTEGER NOT NULL,
  amount       INTEGER NOT NULL,              -- 円
  tendered     INTEGER NOT NULL,              -- 預かり金額（円）
  change_due   INTEGER NOT NULL,              -- お釣り = tendered - amount
  created_at   TEXT NOT NULL,                 -- ISO8601
  ready_at     TEXT,
  served_at    TEXT,
  cancelled_at TEXT,
  UNIQUE (business_day, number)
);
CREATE TABLE order_items (
  order_id  INTEGER NOT NULL REFERENCES orders(id),
  item      TEXT NOT NULL CHECK (item IN ('momo','kawa','negima','tsukune','bonjiri')),
  seasoning TEXT NOT NULL CHECK (seasoning IN ('tare','shio')),
  qty       INTEGER NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, item, seasoning)
);
CREATE TABLE day_settings (
  business_day TEXT NOT NULL,
  key          TEXT NOT NULL,
  value        TEXT NOT NULL,                 -- JSON文字列
  PRIMARY KEY (business_day, key)
);
```

- 採番：`SELECT COALESCE(MAX(number),0)+1 FROM orders WHERE business_day = ?` を注文INSERTと同一トランザクションで
- `day_settings` のキー
  - `capacity`：SKUごとの仕込み本数 `{"momo:tare": 60, ...}`。未設定（null）のSKUは「上限なし」
  - `soldout`：手動で売り切れにしたSKUの配列
  - `cash_float`：釣り銭準備金（円）。初期値 0
- WALモード有効

## 6. 会計ルール（寮祭からの変更）

- `tendered >= amount` でないと確定できない。`change_due = tendered - amount`
- 預かり金額の入力方法：**ちょうど / 1,000 / 5,000 / 10,000 のワンタップ**＋テンキー（100円単位に限らず任意の整数を許可）
- 取り消し（`cancelled`）＝ **全額返金**として扱う。売上・レジ現金の計算から除外する
- 注文の一部変更はしない（取り消して入れ直す）

## 7. 集計の定義（すべて営業日単位。管理画面には2日間合計も出す）

- **販売本数**：cancelled 以外の注文の本数合計（SKU別・串別・味付け別・全体）
- **売上**：cancelled 以外の amount 合計
- **レジ内現金の理論値** = `cash_float` + 売上 … 閉店時に実際の現金と照合する
- **焼くべき本数**：status = waiting の注文の本数合計（SKU別）
- **残り販売可能数**：仕込み数 − 販売本数（SKU別、仕込み数が未設定なら表示しない）
- **平均待ち時間**：直近10件の served 注文の `served_at - created_at` の平均

## 8. 画面

すべて `http://<サーバーのアドレス>:3000/<パス>`。トップ `/` は各画面への大きなリンク集。
見た目は `docs/design.md` と `docs/mock/`（画面モック）に従う。

### 8.1 受付 `/register`（受付PC）
- 5行（串）× 2列（たれ / 塩）の計10ボタン。タップで +1、長押しまたは横の − で −1
- 各ボタンに選択本数と残り販売可能数。売り切れ（残0 または手動売り切れ）は押せない
- 右側：内訳、総本数、**合計金額を特大表示**
- 預かり金額ボタン → **お釣りを特大表示** → 「会計確定 → 番号発行」
- 確定後：**呼び出し番号とお釣りを画面いっぱいに表示** → 同じ番号の整理券を渡す →「次のお客さん」で入力に戻る
- 「クリア」で入力中の内容を破棄
- 直近の注文5件を表示し、waiting のものは取り消しできる（確認ダイアログに返金額を表示）
- 二重送信防止、通信エラー時は画面上部に赤帯（既存どおり）

### 8.2 焼き場 `/grill`（焼き場PC。味付け担当が見て操作する）
- 左（広い）：**waiting の注文を古い順にカード表示**（番号・経過時間・SKU別本数のチップ）。経過10分以上は強調
  - 各カードに「完成」ボタン → ready（渡し場とお客さん用の画面に出る）
  - チップは たれ＝茶、塩＝水色。味付け担当が1注文ぶんをまとめて仕上げられるよう、内訳を大きく
- 右：**SKUごとの「いま必要な本数」**（5行 × 2列、waiting の合計）と合計本数。焼き担当が離れた位置から読める大きさ
- 下：直近で完成にした注文3件と「戻す」（→ waiting）
- 新しく入った注文カードは数秒ハイライト

### 8.3 渡し場・店員用 `/handoff`（渡し場PC その1）
- 左（広い）：**ready の注文を完成した順に表示**（番号を特大、内訳チップ）。新しく完成したものは数秒ハイライト
  - 「渡した」ボタン → served
- 右：このあと来る番号（waiting、表示のみ）、直近 served 3件と「戻す」（→ ready）
- この画面から waiting に戻す操作はない（中身が違っていたら焼き場に声をかけ、焼き場の「戻す」を使う）

### 8.4 渡し場・お客さん用 `/display`（渡し場PC その2。お客さん側に向ける）
- 操作ボタンなし。全画面表示（F11）で使う
- ready の番号を特大表示（「できあがりました！」）。新しく ready になった番号は数秒ハイライト
- waiting の番号を小さく表示（「ただいま焼いています」）
- ロゴ・マスコット・キャッチコピー「一本食べたら もう、トリコ」を配置
- 任意：ready になった瞬間にチャイムを1回鳴らす（ブラウザの自動再生制限があるので、起動時に「音を有効にする」を1回タップさせる。音声ファイルはローカルに同梱）

### 8.5 管理 `/admin`（責任者のスマホ、またはいずれかのPC）
- 営業日の切り替え（1日目 / 2日目 / 合計）
- 売上、販売本数（全体・串別・味付け別・SKU別）
- **レジ締め**：釣り銭準備金の入力、レジ内現金の理論値、実際の金額を入力すると差額を表示
- 待ち件数、平均待ち時間
- 仕込み数の編集（SKUごと）、手動売り切れの切り替え
- 全注文のCSVダウンロード（営業日別、BOM付きUTF-8）
- サーバーのLAN上のURL表示

### 8.6 整理券のQR・お客さん用スマホページ・ミニゲーム（寮祭と同じ仕組みを引き継ぐ）
寮祭では、整理券ごとのQR → Cloudflare Workers 上の公開ページ（`https://taiyaki-status.ryosai2026.workers.dev/?n=<番号>`）で、自分の番号の状況とミニゲームを見られるようにした。
寮祭版のページ構成：ロゴ／番号入力欄と「見る」（QRなら `?n=` で自動入力）／自分の番号と状態／「番号を変える」／ミニゲームへのボタンとランキング（きょう・れきだい）／「お呼び出し中」「焼いています」の番号一覧。
**その実装（サーバーPCからの送信、Worker、整理券の生成、ミニゲーム）をそのまま引き継ぎ、次の点だけ変える。**
既存実装がここに書いた内容と違う場合は既存を優先し、フェーズ0で報告する。

- 公開先：**同じ Cloudflare アカウントに別の Worker として新しくデプロイする**。URLは `https://torico-status.tsudanumasai.workers.dev/?n=<番号>`
  - アカウントの workers.dev サブドメインを `ryosai2026` → `tsudanumasai` に変える（責任者がダッシュボードで実施。取れなければ `tsudanumasai2026`）。寮祭のページのURLも変わるが、寮祭側はもう使わないので問題ない
  - 寮祭の Worker（taiyaki-status）は上書きせず、別名の Worker としてデプロイする（寮祭のコードとデータは記録として残す）
  - 保存先（KV / D1 / Durable Objects など寮祭版が使っているもの）も TORI♡CO 用に新しく作り、寮祭のデータと混ぜない
  - QRのURL形式 `?n=<番号>` と、番号入力欄・「番号を変える」は寮祭版のまま残す
- サーバーPCは数秒おきに「今日の営業日の、番号ごとの状態」と待ち時間の目安を公開先へ送る
  - 送るのは**番号・状態・時刻・待ち時間だけ**。金額や注文内容は送らない
  - 送信は注文処理と切り離す。インターネットが切れても受付〜渡し場は止まらず、復帰したら自動で再開する
  - 管理画面に「公開ページの最終更新時刻」と、切れているときの警告を出す
- お客さん用ページ（スマホ縦画面、宇宙背景）
  - 自分の番号と状態：「ただいま焼いています」／「できあがりました！」／「お渡し済み」
  - **前に待っている組数**（自分より古い waiting の件数）と**待ち時間のめやす**（前の組数 × 直近の1件あたり所要時間。データが少ない間は表示しない）
  - 数秒ごとに自動更新。できあがったら画面全体の色を変えて気づけるようにする
  - 最終更新から60秒以上たっていたら「最新の状況を取得できていません。店頭の画面をご確認ください」と出す
  - 取り消された番号・未発行の番号は「この番号は使われていません」
  - ミニゲームへのボタンとランキング。ランキングは TORI♡CO 用に空から始め、切り替えは「きょう／2日間」
  - 「お呼び出し中」「ただいま焼いています」の番号一覧（寮祭版と同じ）
  - 文言は「番号札」ではなく「整理券」にそろえる
- 営業日：公開ページは「今日」の番号だけを扱う。番号は毎日1からなので、**整理券は2日とも同じ絵柄（1番〜）を使える**
- 整理券：番号ごとにQRが違う。受付は必ず番号順に上から渡す。取り消した注文の整理券は捨てる（寮祭と同じルール）
- ミニゲーム：寮祭のものを残し、素材と配色を TORI♡CO に差し替える（`docs/tasks.md` フェーズ7）

## 9. API（既存の構成を踏襲し、差分のみ）

- `POST /api/orders`：body に `items: [{item, seasoning, qty}]`, `tendered`。サーバー側で金額・お釣りを再計算して検証する
- 一覧・集計系：クエリ `day=YYYY-MM-DD`（省略時は今日）
- `GET/PUT /api/settings`：`day` ごとの `capacity` / `soldout` / `cash_float`
- 状態遷移APIは既存のまま

## 10. 非機能

- 店内の5画面（受付・焼き場・渡し場×2・管理）は外部API・CDN・Webフォントの外部読み込み禁止。フォントも画像も音も同梱する
- 外に出てよい通信は、8.6 の公開ステータスへの送信だけ。失敗しても店内の動作に一切影響させない
- 画面更新は2秒間隔のポーリング（既存どおり）。端末4台＋スマホ数台で問題ない負荷
- サーバーが落ちても再起動でデータが残ること
- ボタンは最低 64px 高。現場で1タップで完結させる
